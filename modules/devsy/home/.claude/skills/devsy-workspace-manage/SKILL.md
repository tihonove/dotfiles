# Воркспейсы devsy: жизненный цикл

Заведение нового — в скиле `devsy-workspace-up`, там же описано, что уже
настроено в контексте и куда пишутся ssh-алиасы.

Ключевая особенность: **контейнер живёт на облачной машине, а метаданные о нём —
локально**, в `~/.devsy/contexts/default/workspaces/<id>/workspace.json`. Почти
все странности («воркспейса нет», «поднялся пустой») — про рассинхрон этих двух
половин.

## Посмотреть

```sh
devsy ws list                # весь список
devsy ws describe <имя>      # подробности одного
devsy ws status <имя>        # Running / Stopped / NotFound
devsy ws logs <имя>          # логи контейнера
devsy ws exec <имя> -- <cmd> # команда внутри, без ssh-сессии
```

Вывод — json, когда не в терминал (то есть всегда, когда его читает агент).
Разбирать `python3 -c` / `jq`, а не глазами по строкам.

Что стоит знать про статус: воркспейсы **сами останавливаются по простою** —
2 часа в облаке, 1 час локально. `Stopped` — это норма, а не поломка; будится
`devsy ws up <имя>`.

## Изменить

```sh
devsy ws stop <имя>                 # остановить, данные на месте
devsy ws up <имя> --recreate        # пересобрать контейнер, источник оставить
devsy ws up <имя> --reset           # пересобрать вместе с источником
devsy ws rename <старое> <новое>
```

`--recreate` — правильный ответ на «поменял devcontainer.json» и на «контейнер
встал криво». `--reset` дополнительно сносит склонированную репу: всё
незапушенное внутри пропадёт.

## Удалить

```sh
devsy ws delete <имя>                    # контейнер и метаданные
devsy ws delete <имя> --remove-volumes   # и тома вместе с ними
```

Удаление — необратимое и молчаливое: работа внутри воркспейса не в git, пока её
туда не отправили. **Перед удалением спросить человека** и заодно проверить, не
осталось ли внутри незапушенного:

```sh
devsy ws exec <имя> -- git -C /workspaces/<имя> status --short
```

Каталог внутри контейнера — `/workspaces/<id воркспейса>`, а не имя репы: id и
имя папки совпадают, даже когда репа называется иначе.

`--force` нужен только когда контейнер на машине уже мёртв, а локальная запись
осталась — иначе delete упрётся в «not found».

После удаления заглянуть в `~/.ssh/config.d/devsy.conf`: свои блоки devsy метит
`# Devsy Start/End` и снимает их сам, но блоки, заведённые руками в `local.conf`
до того, как devsy стал писать их сам, он не трогает — эти снимать вручную.

## Воркспейс не виден на новой машине

Симптом: контейнер на облачной машине жив (`ssh devsy-host docker ps -a`), а
`devsy ws list` пуст, и `devsy ws up <repo>` поднимает **новый** контейнер вместо
подключения к старому. Причина — нет локальных метаданных: имя образа и томов
содержит uid воркспейса, а uid берётся именно из них.

Спасает копия, которую держит агент на хосте:

```sh
ssh devsy-host 'cat ~/.devsy/contexts/default/workspaces/<id>/agent/workspace.json' \
  | python3 -c 'import json,sys,os;
      w=json.load(sys.stdin)["workspace"];
      d=os.path.expanduser("~/.devsy/contexts/default/workspaces/"+w["id"]);
      os.makedirs(d, exist_ok=True);
      json.dump(w, open(d+"/workspace.json","w"), indent=2)'
```

После этого `devsy ws list` покажет воркспейс, `status` вернёт `Running`, а
`ssh <имя>.devsy` зайдёт в существующий контейнер. Проверять до и после —
`ssh devsy-host docker ps -a`: id и uptime контейнеров меняться не должны.

## Чего не делать

- **не удалять и не пересобирать без спроса.** `delete`, `--reset`,
  `--remove-volumes` уносят данные, которых нет больше нигде;
- **не чинить рассинхрон повторным `up` из репы** — это ровно тот путь, который
  плодит второй контейнер рядом с первым. Сначала восстановить метаданные;
- **не править `~/.devsy/config.yaml` и `~/.ssh/config` руками** — первый
  воспроизводится `~/.dotfiles/modules/devsy/setup`, второй симлинк в репу.
