# Поднять воркспейс devsy

`devsy` — CLI поверх devcontainers. Воркспейс = контейнер + метаданные о нём;
контейнер живёт либо на облачной машине (провайдер `ssh`), либо тут же в podman
(провайдер `docker`).

## Что уже настроено — не переспрашивать и не переделывать

Всё это разложено `~/.dotfiles/modules/devsy/setup`, проверять перед каждым `up`
не нужно:

- контекст `default`, провайдер по умолчанию — `ssh` (облачная машина);
- IDE — `none`. Никакой браузер и VSCode при `up` не открывается, это осознанно;
- дотфайлы: `DOTFILES_URL` + `DOTFILES_SCRIPT=install.sh`. В новом контейнере
  сами разложатся симлинки и поставятся тулы `core` — второго шага руками нет;
- ssh-алиас: `SSH_CONFIG_INCLUDE_PATH=~/.ssh/config.d/devsy.conf`. `Host`-блок
  для нового воркспейса devsy дописывает туда **сам**, руками писать не надо.

Адрес облачной машины лежит вне репы, в `~/.config/devsy-setup.conf`.

## Облако или локально

По умолчанию — **облако**. Локальный podman берём, только если человек попросил
явно, или если задача в том, чтобы прогнать `devcontainer.json` побыстрее и без
сети до облака.

| | облако (`ssh`) | локально (`docker`/podman) |
|---|---|---|
| источник | git-репа, клонируется на машине | локальная папка, бинд-маунт |
| ресурсы | машины, а не ноутбука | ноутбука |
| простой | останавливается через 2 ч | через 1 ч |
| имя | `<repo>` | `<repo>-local` |

## Облачный воркспейс

```sh
devsy ws up git@github.com:tihonove/<repo>.git --id <имя>
```

- `--id` можно опустить — тогда имя берётся из имени репы. Задавать его нужно,
  когда на одну репу заводится второй воркспейс (так живут `vexx` и
  `vexx-local`): id — это ключ, по которому devsy отличает контейнеры;
- сборка долгая. Если ждать в чате нечего — `-d`, а прогресс смотреть
  `devsy ws task logs <task-id> -f`;
- приватная репа клонируется по ssh: агент прокидывается в контейнер, ключи
  ничего дополнительно не требуют.

## Локальный воркспейс

```sh
devsy ws up . --provider docker --id <имя>-local
```

Провайдер называется `docker`, но под ним podman (`DOCKER_PATH=podman`) — это
одна и та же настройка, не путать с реальным docker'ом.

Если `devsy provider list` его не показывает (новая машина), завести:

```sh
devsy provider add docker -o DOCKER_PATH=podman -o INACTIVITY_TIMEOUT=1h
```

Флага `--use` тут быть не должно: провайдером по умолчанию остаётся `ssh`,
локальный выбирается флагом `--provider` на конкретный `up`.

## Уже заведённый воркспейс

`up` по **имени** не создаёт новый, а поднимает существующий:

```sh
devsy ws up <имя>          # разбудить после простоя
ssh <имя>.devsy            # зайти, пользователем vscode
```

Заходить лучше через ssh-алиас, а не `devsy ws ssh`: через него работают
scp/rsync и VSCode Remote-SSH.

## После up — проверить

```sh
devsy ws status <имя>
ssh <имя>.devsy 'command -v starship'
```

`starship` ставит `modules/core/update`, так что найденный бинарь означает, что
дотфайлы в контейнере отработали целиком, а не только склонировались.

## Чего не делать

- **не дописывать `Host`-блоки в `~/.ssh/config`** — это симлинк в репу, правка
  уедет под гит. Блоки воркспейсов devsy пишет сам в `~/.ssh/config.d/devsy.conf`,
  прочий инвентарь (адреса машин) — руками в `~/.ssh/config.d/local.conf`;
- **не править `~/.devsy/config.yaml` руками.** Он воспроизводится скриптом
  `~/.dotfiles/modules/devsy/setup`; менять надо скрипт и прогонять его, иначе
  настройка не переживёт новую машину;
- **не открывать IDE** через `--ide`. Подключение — ssh или VSCode Remote-SSH
  по месту.

Разбор списка, остановки, удаления и восстановления метаданных — в скиле
`devsy-workspace-manage`.
