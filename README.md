# dotfiles

Личные конфиги. Собираются заново — старая версия лежит в `~/dotfiles-old`
и переезжает сюда по кусочкам, осознанно.

## Структура

```
.
├── install.sh         # раскладывает симлинки
├── lib/tools.sh       # общее для установщиков модулей
├── README.md
├── modules/
│   └── <модуль>/
│       ├── home/        # зеркало ~ : home/<path> -> ~/<path>
│       ├── module.conf  # desc, requires, scripts
│       └── update       # ставит внешние бинарники; запускается руками
└── system/          # то, что ставится в /etc руками, под sudo
```

В корне репы — только служебное. Всё, что реально попадает в домашний
каталог, живёт в `home/` какого-нибудь модуля.

Дальше по тексту пути даются относительно `home/` модуля: `.config/starship.toml`
значит «файл, который лёг в `~/.config/starship.toml`». Из какого он модуля —
смотреть `./install.sh list`, и специально не указано: файл может переехать
между модулями, а путь в `~` от этого не меняется.

## Модули

Payload разложен по модулям, чтобы база вставала на любой машине, а тяжёлые
подсистемы — только там, где им есть на чём работать. Конфиг sway на сервере
без Wayland не нужен, а раньше приезжал вместе со всем остальным.

| модуль | что внутри | requires |
|---|---|---|
| `core` | bash, ble.sh, fzf, starship, tmux, btop, палитра темы (`theme-colors`) | — |
| `kitty` | терминал, шрифты (`fontconfig`), `ssh.conf` для kitten ssh | `kitty` |
| `sway` | сессия целиком: sway, waybar, wofi, kanshi, тема, мониторы, история буфера | `sway waybar wofi kanshi wtype cliphist jq` |
| `devsy` | `~/.ssh/config` + установка CLI и настройка ssh-провайдера | — |
| `vexx` | только скрипт обновления бинарника | — |

Цель симлинка считается от пути **внутри `home/`**, а не от имени модуля.
Поэтому файл можно двигать между модулями свободно: в `~` ничего не появляется
и не исчезает, меняется только то, куда указывает симлинк. `--dry-run` покажет
это как `relink` — ноль изменений он не покажет, имя модуля входит в путь
источника. Для программ, читающих конфиг сквозь симлинк, переезд прозрачен.

Одна оговорка про порядок: между перемещением файла в репе и `./install.sh`
симлинк указывает в никуда. Если в это окно программа перечитает конфиг, она
его не найдёт — sway, например, молча свалится на `/etc/sway/config`. Двигать и
устанавливать нужно подряд.

Какие модули ставить, решает `~/.config/dotfiles/profile` — файл **вне репы**,
по той же конвенции, что `~/.ssh/config.d/*.conf` (см. «Инвентарь»): состав
машины — машинно-специфичная вещь, публичной репе про неё знать незачем.
Формат — имя модуля на строку, `#`-комментарии игнорируются. Профиля нет —
ставится один `core`, он включён всегда и выключить его нельзя.

```sh
./install.sh list           # что есть, что включено, чего не хватает в системе
./install.sh add sway       # включить в профиле и сразу поставить
./install.sh remove sway    # выключить; симлинки НЕ снимает, а показывает какие
```

`remove` намеренно не удаляет файлы из `~`: молча сносить что-то в домашнем
каталоге скрипт не должен, поэтому он печатает список `rm ~/...` и оставляет
решение человеку.

В `module.conf` — `desc` для `list`, `requires` и `scripts`.

`requires` — команды, без которых модуль бессмыслен. Это не автоопределение, а
предохранитель. Модуль включён, а бинаря нет — предполётная проверка отказывает
целиком, а не пропускает модуль молча: тихий пропуск выглядит как успешная
установка, после которой ничего не работает.

У `devsy` и `vexx` поле пустое намеренно, хотя бинарники им нужны: их же
скрипты эти бинарники и ставят. Требовать наличия того, что модуль сам
приносит, — замкнутый круг; вместо этого скрипты падают сами и с внятным
текстом.

`scripts` — скрипты модуля. Один из них особый по имени: **`update` запускает
сам `install.sh`** после раскладки симлинков. Так и должно быть — симлинк на
`starship.toml` при отсутствующем `starship` не делает ничего, а установка,
после которой ничего не работает, установкой не является. Остальные скрипты
(`devsy/setup`) только показываются в `list` и запускаются руками.

Два правила, без которых это ломало бы `install.sh` как инструмент:

- **сбой установщика не роняет установку.** Симлинки к этому моменту уже
  разложены и корректны; нет сети — это причина сказать «тулы не обновились», а
  не откатывать сделанное. Код возврата при этом ненулевой, а в конце печатается,
  что доделать;
- **установщик обязан быть дешёвым, когда ставить нечего.** Каждый `update`
  сверяет установленное с актуальным и молча пропускает совпавшее. Полный
  прогон вхолостую — около 3 секунд, и это целиком обращения к GitHub API.

Если нужны только симлинки — `./install.sh --no-tools`, это 0.2 секунды.

Модуль, состоящий из одного скрипта и не имеющий `home/`, — нормальная
ситуация (`vexx`), а не повод для предупреждения.

## Установка

Одной строкой, на любой машине и в любом состоянии:

```sh
bash -c "$(curl -fsSL https://raw.githubusercontent.com/tihonove/dotfiles/main/bootstrap.sh)"
```

`bootstrap.sh` сам разбирается, что перед ним, и делает одно из трёх: клонирует
и ставит, если репы нет; обновляет через `update.sh`, если стоит модульная
схема; переводит на неё, если лежит старая версия.

Миграция — не косметика, а то, что иначе делается руками и делалось трижды:

- **снимок**: ветка `old-scheme` в репе плюс копия дерева в `~/dotfiles-old`.
  Именно ветка, а не тег: наш же конфиг ставит `fetch.pruneTags = true`, и
  первый же fetch снёс бы локальный тег вместе со страховкой. Проверено —
  ровно так тег и пропал на живой машине;
- **спасение данных, живущих внутри репы**. На рабочей машине `~/.claude` был
  симлинком в `~/.dotfiles/.claude`, а там 173 МБ истории и проектов; каталог в
  `.gitignore`, так что `git clean -ffdx` снёс бы его молча. Отличаем данные от
  конфигов по git: цель симлинка отслеживается — это содержимое репы, симлинк
  просто снимается; не отслеживается и это каталог — выносим наружу, на место
  симлинка;
- **локальные слои**: `~/.bashrc.local` и `~/.gitconfig.local` прежней схемы
  переезжают в `~/.bashrc` (вне блоков) и `~/.gitconfig`. На рабочей машине там
  корпоративное окружение и рабочая личность — терять нечего и нельзя;
- **снятие старой раскладки**: убираются все симлинки, ведущие в репу, и
  опустевшие после этого каталоги.

Скрипт не ставит пакеты, не трогает `/etc` и не просит sudo: всё, что он меняет,
лежит в `~` и снимается через `uninstall.sh`.

Вручную, если хочется по шагам:

```sh
git clone https://github.com/tihonove/dotfiles.git ~/.dotfiles
~/.dotfiles/install.sh
```

Линкуются файлы, а не каталоги: `install.sh` обходит `home/` включённых модулей
в глубину, создаёт недостающие каталоги в `~` обычными и делает симлинк на
каждый файл.
Каталог целиком под симлинк не уходит никогда — поэтому в `~/.config` спокойно
соседствуют файлы из репы и состояние чужих программ, и последние не трогаются.
Существующие файлы сохраняются рядом с суффиксом `.backup.YYYYMMDD_HHMMSS`.

Посмотреть, что произойдёт, ничего не меняя:

```sh
~/.dotfiles/install.sh --dry-run
```

Сначала строится план и проверяется целиком, и только потом выполняется. Если
хоть что-то не так — установка не начинается вовсе. Отказ вызывают:

- на пути к нашему файлу лежит **не каталог** (`~/.config/sway` файлом, когда
  нужен `~/.config/sway/config`) — раньше на этом падал `mkdir`, уже посреди
  установки: часть симлинков стоит, часть нет, отката нет;
- на месте нашего файла лежит **каталог**. Прежняя версия унесла бы его целиком
  в `.backup.*` — данные бы выжили, но приложение сломалось бы молча. Такое
  решение принимает человек;
- в профиле **модуль, которого нет** в `modules/`;
- у включённого модуля **не выполнены `requires`**;
- два модуля дают **один и тот же путь** в `~`. До модулей такое было
  невозможно, теперь возможно, и исход решал бы порядок установки — молча.

Предупреждениями (установку не останавливают) отмечаются симлинк вместо
промежуточного каталога — файлы лягут в его цель, — модуль без `home/` и без
`scripts` (то есть не делающий вообще ничего) и симлинки внутри `home/`: их
`find -type f` не видит, и установлены они не будут.

Повторный запуск идемпотентен и показывает, что реально изменилось: уже
правильные симлинки считаются на месте, а не пересоздаются.

## Обновление

```sh
~/.dotfiles/update.sh --dry-run   # что приедет и что снимется
~/.dotfiles/update.sh
```

Подтягивает репу и приводит раскладку в соответствие с новым содержимым.
Почти то же, что `git pull && ./install.sh`, — но не совсем, и разница
принципиальная.

`install.sh` строит план по **текущим** деревьям модулей. Файл, удалённый из
репы, в план не попадает вовсе: его симлинк в `~` после pull повисает битым и
остаётся таким навсегда. `uninstall.sh` обходит те же деревья и тоже его не
видит. Это ровно тот мусор, который пришлось выковыривать руками при переезде со
старой схемы.

Устаревшее ищется **по данным git** — `git diff --no-renames --diff-filter=D`
между старым и новым HEAD, — а не обходом домашнего каталога: точнее и быстрее,
а главное, не заденет чужие битые симлинки, которых в `~` хватает и без нас
(Chrome, pulse). Снимается только симлинк, ведущий ровно на исчезнувший путь.

`--no-renames` тут не мелочь. По умолчанию git засчитывает переезд файла между
модулями как переименование, старый путь в удалённые не попадает, и спасает
только `relink` в `install.sh` — ровно до тех пор, пока файл переезжает во
**включённый** модуль. Уехал в тот, которого на машине нет, — старый симлинк
остался бы висеть.

Отказы: незакоммиченные правки **отслеживаемых** файлов (pull их не переживёт;
неотслеживаемые не мешают и не блокируют), отсутствие upstream у ветки и
разошедшиеся ветки — `pull` делается только перемоткой, молчаливый merge-коммит
в конфигах никому не нужен.

Дальше запускается обычный `install.sh`, которому и передаются `--dry-run` с
`--no-tools`: своей логики раскладки в `update.sh` нет намеренно — дублировать
её значит однажды получить две разные.

## Снятие

```sh
~/.dotfiles/uninstall.sh --dry-run   # что будет снято
~/.dotfiles/uninstall.sh
```

Обратная операция к установке, и написана она по той же причине, по которой
существует `install.sh`: раскладка ставится одной командой, а снималась руками
и на каждой машине заново — найти симлинки, не спутать их с чужими, вспомнить
про блоки в `~/.bashrc`.

Удаляется только то, про что точно известно, что это наше: **симлинк,
указывающий ровно на наш файл в репе**. Обычный файл на нашем пути не трогается
(значит, чужой лёг на то же место), симлинк в чужую сторону — тоже. И то, и
другое печатается списком в конце. Снятие поэтому безопаснее установки: та хотя
бы уносила файлы в `.backup`, эта не удаляет ничего, чего не создавала.

Берутся **все модули репы**, а не только включённые в профиле — потому что
`install.sh remove <мод>` симлинки не снимает и честно об этом пишет, так что на
машине запросто лежит раскладка модуля, которого в профиле давно нет.
Ограничить профилем — `--profile`.

Не трогается намеренно:

| что | почему |
|---|---|
| `~/.gitconfig` | локальный слой: туда пишут и devsy, и `git config --global` |
| `~/.ssh/config.d/` | инвентарь, он в репу и не уезжал |
| `~/.config/dotfiles/profile` | машинный выбор модулей; убрать вместе со всем — `--purge` |
| `~/.local/bin/*`, `blesh` | это тулы от `modules/*/update`, а не раскладка; тот же `fzf` мог приехать и не от нас |

Последние две строки `--purge` всё-таки убирает — профиль и `~/.gitconfig`, но
второй только если тот пуст по содержанию: непустой уже чей-то локальный слой.
Блоки из `~/.bashrc` вырезаются вместе с маркерами, всё остальное в файле
остаётся как было — оно пережило установку, значит обязано пережить и снятие.

## Почему ~/.bashrc не симлинк

Единственный файл, который раскладывается не симлинком. Корпоративные
утилиты имеют привычку дописывать себя в `~/.bashrc` — обычно добавляют
что-то в `PATH`. Если `~/.bashrc` симлинк в репу, они пишут в файл под
гитом: вечно грязный `git status`, риск закоммитить машинно-специфичное в
переносимую репу и — хуже всего — молчаливая потеря их строк на первом же
`git checkout`, после которого утилита ломается без внятной причины.

Поэтому наоборот: `~/.bashrc` — обычный локальный файл, а `install.sh`
дописывает в него **два** маркированных блока:

```sh
# >>> dotfiles >>>
[ -f "$HOME/.config/bash/rc.sh" ] && . "$HOME/.config/bash/rc.sh"
# <<< dotfiles <<<

        ...здесь чужое: PATH корпоративных утилит, чужой PS1...

# >>> dotfiles prompt >>>
[ -f "$HOME/.config/bash/prompt.sh" ] && . "$HOME/.config/bash/prompt.sh"
# <<< dotfiles prompt <<<
```

Блоков два, потому что у частей конфига **противоположные** требования к
порядку.

**Ранний — в начало**, так как чужие инсталляторы дописывают себя в конец: их
`PATH` ложится позже нашего и побеждает при конфликте имён. Это то, что нужно —
корпоративные тулзы должны работать, а в `~/.local/bin` лежит только своё.

**Поздний — в конец**, ровно по обратной причине. Чужой `~/.bashrc` может
задавать свой `PS1` ниже: так делает базовый образ devcontainer (функция
`__bash_prompt`). Пока промпт настраивался в раннем блоке, `starship`
отрабатывал первым и через полторы сотни строк его молча затирали — со стороны
это выглядело так, будто starship вообще не установлен. Всё, что борется за
`PS1` и `PROMPT_COMMAND`, живёт в `prompt.sh`; всё остальное — в `rc.sh`.

Там же и `ble-attach`: он обязан идти после `starship`, иначе ble.sh займёт
`PROMPT_COMMAND` первым. Загрузка ble.sh при этом остаётся в раннем блоке —
с `--attach=none` она сама по себе промпта не трогает.

Обе дописки идемпотентны: есть маркер — `install.sh` файл не трогает.

Всё, что в `~/.bashrc` вне блоков, считается машинно-локальным и в репу не
уезжает. Посмотреть, что там накопилось:

```sh
~/.dotfiles/install.sh --check
```

Тот же приём уже применён к `~/.ssh/config`, только по другой причине — см.
«Инвентарь», и к `~/.gitconfig` — см. «git», где локальный слой обеспечивает
сам git порядком чтения файлов.

## git

Конфиг перенесён из `~/dotfiles-old/.gitconfig`, но лежит по XDG-пути
`.config/git/config`, а не в `~/.gitconfig`. Это не вкусовщина: так локальный
слой даёт сам git, без единого `include`.

git читает конфиги в порядке `system` → `~/.config/git/config` → `~/.gitconfig`,
и побеждает прочитанное позже. Значит `~/.gitconfig` естественно перекрывает
управляемый файл — рабочая почта, чужие credential-хелперы, всё машинное, — а
незаданные там ключи проваливаются в репный.

Но главное не это, а вот что: **`git config --global` пишет в `~/.gitconfig`,
только если тот существует**; иначе — в `~/.config/git/config`, то есть прямо в
гит-репу. Проверено, ведёт себя ровно так. Поэтому `install.sh` следит, чтобы
`~/.gitconfig` существовал, и создаёт его пустым (с комментарием) — это второй
файл после `~/.bashrc`, который намеренно НЕ симлинк.

Что записи туда реальны, видно на devsy-контейнере: там `~/.gitconfig` уже
заведён самим devsy — он кладёт в него свой credential-хелпер. Будь этот путь
симлинком в репу, повторилась бы история с `~/.ssh/config`.

Рабочая личность заводится обычным способом, ничего специального:

```sh
git config --global user.email you@work.example
```

Посмотреть, кто победил, — `git config --list --show-origin`. Именно **без**
`--global`: с ним git показывает только `~/.gitconfig` и XDG-слой не видит.

Две вещи в конфиге стоят объяснения:

- **редактор задаёт модуль vexx**, а не общий конфиг. `core.editor = vexx` на
  машине без vexx ломал бы `git commit` без `-m` — а в devsy-контейнере vexx
  нет. Поэтому в управляемом конфиге стоит `[include] path =
  ~/.config/git/vexx.conf`, а сам файл приносит модуль `vexx`. Отсутствующий
  include git молча игнорирует, так что без модуля строка не делает ничего;
- **глобальный `.gitignore`** — это `.config/git/ignore`, и `core.excludesfile`
  для него не нужен: git читает этот путь сам.

Из старого конфига намеренно не переехали credential-хелперы для github через
`gh`: они были прописаны абсолютным `/usr/bin/gh`, которого на этой машине нет
вовсе, а в контейнере учётками занимается devsy. Понадобится — это ровно тот
случай, для которого заведён локальный слой.

## Инвентарь

Отдельная от секретов категория, которую легко перепутать. Секретов в репе нет
по определению — ключи, токены и пароли сюда не кладутся никогда. Но есть
данные, которые секретом не являются и всё равно не должны быть публичными:
адреса машин, имена воркспейсов, пользователи, под которыми туда ходишь.

Разница практическая. Секрет утекает один раз, и его меняют. Инвентарь — это
карта: она остаётся верной годами и читается как список целей. Отдельно это
касается рабочих хостов: ssh-конфиг ровно то место, куда рано или поздно
приезжают корпоративные имена и бастионы.

Репа публичная намеренно — так её можно развернуть на любой машине одной
командой, без аутентификации. Значит, инвентарь живёт снаружи:

| что | где лежит | как подключается |
|---|---|---|
| `Host`-блоки ssh | `~/.ssh/config.d/*.conf` | `Include` первой строкой `~/.ssh/config` |
| адрес машины devsy | `~/.config/devsy-setup.conf` | `modules/devsy/setup` читает при запуске |

В репе на их месте — шаблоны и объяснения, то есть та часть, которая
переносима и которую стоит помнить. Хосты подставляются на месте.

`Include` в ssh стоит первым не случайно: в `ssh_config` выигрывает не
последнее значение опции, а первое встреченное, так что локальный слой должен
идти раньше всего, что мог бы перебить. Отсутствующий каталог или маска без
совпадений ошибкой не считаются.

## Внешние тулзы

У каждого модуля свой установщик — `modules/<модуль>/update`. Их запускает
`install.sh` (см. «Модули»), но можно дёрнуть и по одному:

```sh
~/.dotfiles/modules/core/update    # starship, ble.sh, fzf, kitten
~/.dotfiles/modules/kitty/update   # шрифты
~/.dotfiles/modules/devsy/update   # devsy CLI
~/.dotfiles/modules/vexx/update    # vexx
```

Раньше это был один `modules/<модуль>/update` в корне, и он ставил всё сразу. Разрез по
модулям — не косметика, а следствие двух вещей, вскрывшихся на контейнере:

- **всё или ничего.** Скрипт начинался с гарда `uname -m != aarch64` → `exit 1`
  и падал целиком, хотя шрифты и ble.sh от архитектуры не зависят вовсе. Теперь
  архитектура проверяется только там, где она реально нужна (`arch_for` в
  `lib/tools.sh`), и заодно понимает x86_64;
- **лишнее в чужой среде.** В контейнере нет `fc-cache`, и шаг со шрифтами ронял
  скрипт под `set -e` — starship успевал поставиться, а ble.sh после него уже
  нет. Плюс туда же приезжали 122 МБ devsy, которому в контейнере делать нечего.
  Теперь контейнеру хватает `modules/core/update`, а шрифты сами себя пропускают,
  если fontconfig в системе нет.

Общее (`github_latest_version`, `arch_for`, `BIN_DIR`) вынесено в `lib/tools.sh`.
Лежит в `lib/`, а не в `modules/`: `install.sh` считает модулем каждый каталог в
`modules/`, и библиотека показалась бы в `list` отдельной строкой.

Бинарники в git не кладём: в старых dotfiles вендоренный `.starship.arm` был
собран под 32-битный ARM и на aarch64 не падал, а вешал старт шелла намертво.
Сборки берём musl — не зависят от версии glibc.

**Ни одного sudo.** Всё кладётся в `~/.local`, поэтому работает и там, где прав
нет. starship при этом есть и пакетом (Ubuntu 26.04, 1.22), но уже установленный
`starship` установщик не трогает, откуда бы тот ни взялся: подкладывать поверх
свою копию в `~/.local/bin` — верный способ однажды запутаться, какая из двух в
`PATH`. Нет пакета — качается бинарник, и он свежее пакетного.

## Свой софт (догфуд)

```sh
~/.dotfiles/modules/vexx/update
```

Отдельно от остальных: своё обновляется часто и по одному, внешнее — редко и
пачкой. Хочется дёрнуть сразу после своей же сборки, не перекачивая шрифты и
ble.sh.

- **vexx** — редактор, ставится в `~/.local/bin` из релиза `nightly`.
  Версия — коммит (`nightly-a791c81`); если установленный совпадает с релизом,
  скрипт не качает 45 МБ заново. В старых dotfiles arm64-сборки не было и на
  этой машине vexx просто пропускался — сейчас ассет `vexx-linux-arm64` есть.

## Что внутри

- `.config/bash/rc.sh` — управляемая часть `.bashrc`, минимальная, растёт по
  шагам; подключается блоком из `~/.bashrc`, см. «Почему ~/.bashrc не симлинк»
- **starship** — промпт, конфиг `.config/starship.toml`
- **tmux** — конфиг `.config/tmux/tmux.conf`, тема и меню-бар. Подробности ниже
- **btop** — системный монитор, конфиг `.config/btop/btop.conf`: три строки,
  всё остальное — дефолты btop. Тема — общая палитра сессии, см. «Тема»; рядом
  лежит обёртка `.local/bin/btop`, которая эту тему обновляет перед запуском —
  нужна на машинах, где `theme-toggle` не живёт
- **шрифты** — цепочка фолбэков собирается в `.config/fontconfig/fonts.conf`:
  - **JetBrainsMono Nerd Font** — дефолтный `monospace`, ставится в
    `~/.local/share/fonts` через `modules/<модуль>/update`
  - **Symbola** — всё, чего нет в Nerd Font: блок Miscellaneous Technical
    (`⏵` U+23F5, `⎿` U+23BF в TUI Claude Code) и эмодзи по Unicode 9
    включительно (`✅ ❌ 💡`), монохромом. Ставится пакетом, см. «Пакеты»
  - **Noto Color Emoji** — цветные эмодзи новее Unicode 9 (`🥲 🫠`), которых нет
    даже в Symbola; ставится в `~/.local/share/fonts` через `modules/<модуль>/update`
- **sway** — база (раскладки, тачпад, тема, автозапуск панели), биндов почти нет.
  Навигация трёхуровневая: `$mod+Ctrl+h/l` — столы, `$mod+h/l` — окна и табы
  sway, `$mod+Alt+h/l` — вкладки внутри окна (Chrome, окна tmux), скрипт
  `.local/bin/content-tab`
- **тема** — светлая/тёмная переключается для всей сессии разом, скрипты
  `.local/bin/theme-toggle` и `theme-colors`. Подробности ниже
- **мониторы** — `$mod+P`, скрипт `.local/bin/display-setup`, профили в
  `.config/kanshi/config`. Подробности ниже
- **waybar** — панель, порт стокового конфига без мёртвых модулей
- **wofi** — лаунчер по `$mod+d`, конфиг и тема в `.config/wofi/`.
  Своей темы у wofi нет вовсе: без `style.css` он рисуется дефолтной GTK-темой
  и в тёмной сессии выглядит чужеродно. Палитра — та же, что у sway и waybar, и
  переключается вместе с темой (см. «Тема»). Шрифт запрошен как `monospace` — алиас из `fonts.conf` уводит его на
  **NFM**, то же начертание, что у kitty. Это не мелочь: в системе лежат оба,
  `JetBrainsMono Nerd Font` (NF) и `... Nerd Font Mono` (NFM), у второго
  Nerd-глифы ужаты в ячейку сетки. Waybar просит NF намеренно — иконкам панели
  ужатие ни к чему; лаунчер же стоит рядом с терминалом, и разные ширины в нём
  сразу читаются как «шрифт другой». Размер 14px против 13px в панели (у kitty
  11pt, что при scale 1.0 даёт ≈14.7px). Режим `drun` задан в конфиге, а не в
  строке запуска, чтобы голый `wofi` из терминала вёл себя как бинд
- **ble.sh** — автодополнение и подсветка в bash; ставится в
  `~/.local/share/blesh`, конфиг `.config/blesh/init.sh`
- **fzf** — `C-r` по истории, `C-t` по файлам, `M-c` по каталогам; из пакета,
  подключается модулями ble.sh, см. раздел «fzf»
- **буфер обмена** — `.local/bin/clip`: копирование файлов между машинами через
  TTY, работает сквозь ssh и `docker exec`. Подробности ниже
- **история буфера** — `$mod+v`, скрипт `.local/bin/clip-history`: хранит
  cliphist, показывает тот же wofi с тем же `style.css`, что и лаунчер (свой
  `.config/wofi/clip-history.conf` — только dmenu и картинки), вставляет
  выбранное через `wtype`. Подробности ниже

## fzf

fzf подключается не как у всех. Обычный рецепт —
`eval "$(fzf --bash)"` в `.bashrc` — с ble.sh не работает: ble.sh заменяет
собой readline, и `bind -x`, на которых держатся виджеты fzf, до него не
доходят. В лучшем случае клавиши молчат, в худшем рвётся отрисовка строки.

Апстрим ble.sh это предусмотрел и держит модули-обёртки, которые отдают
терминал fzf на время работы виджета и забирают обратно. Подключаются они из
blerc, то есть из `.config/blesh/init.sh`:

```bash
ble-import -d integration/fzf-completion
ble-import -d integration/fzf-key-bindings
```

Тонкости, из-за которых это выглядит именно так:

- `-d` (отложенная загрузка) — не оптимизация, а порядок: `fzf-completion`
  обязан грузиться после `bash-completion`, а тот подключается в `rc.sh` уже
  после `ble.sh`. С `-d` модуль ждёт конца инициализации;
- каталог со скриптами fzf модуль ищет сам и на Ubuntu находит
  `/usr/share/doc/fzf/examples` — но это уже не обязательно. Для fzf >= 0.48
  он переключается на `base=__eval_fzf_bash__`, то есть берёт интеграцию прямо
  из `fzf --bash` (см. `contrib/integration/fzf.common.bash`). Поэтому голого
  бинарника достаточно, и `modules/core/update` ставит именно его — раньше
  считалось, что нужен непременно пакет, и из-за этого fzf не оказывался нигде,
  кроме машин, где его поставили руками;
- в `rc.sh` остался обычный `eval "$(fzf --bash)"`, но под условием
  `[[ ! ${BLE_VERSION-} ]]`: это запасной путь для сессии без ble.sh (свежая
  машина до `modules/<модуль>/update`), иначе fzf остался бы вовсе без биндингов;
- `--color=16` в `FZF_DEFAULT_OPTS` — то, из-за чего fzf следует теме: он
  рисует ANSI-цветами, а палитру 0..15 kitty перекрашивает на лету по
  `theme-toggle`. Дефолтная схема fzf прибита к 256-цветным значениям под
  тёмный фон и в светлой теме читается плохо.

## tmux

Конфиг перенесён из `~/dotfiles-old/.tmux.conf` целиком: prefix `C-s`, лейауты с
`main-vertical` по умолчанию, дубли всех дефолтных биндов на русскую раскладку,
двухстрочный статус сверху с кликабельным меню-баром (Sessions / Windows /
Panes / System) и тема catppuccin mocha.

Путь — `.config/tmux/tmux.conf`, а не `~/.tmux.conf`: tmux с 3.1 ищет и там, а
так весь конфиг живёт в `~/.config`.

Изменено при переносе только то, что на этой машине физически не работало;
в конфиге каждое такое место помечено `ПЕРЕНОС:`.

- **копирование** было через `xsel`, а это X11 и в системе его нет — все четыре
  бинда были мертвы. Заменено на `set -clipboard on`: tmux отдаёт выделенное
  самому терминалу через OSC 52, kitty это умеет. `wl-copy` не подошёл бы —
  по ssh он писал бы в буфер удалённой машины, а не своей;
- **бинды копирования** висели на таблице `copy-mode-vi`, но `mode-keys` здесь
  `emacs` (vi включился бы, только если в `$EDITOR` есть «vi», а там `vexx`),
  так что половина не срабатывала. Теперь биндится и `copy-mode`, и
  `copy-mode-vi`;
- **пути** `~/.tmux_plugins/` и `~/.dotfiles.scripts/` из старой схемы на машине
  уже не существуют. Плагин переехал в `~/.local/share/tmux/catppuccin`, туда же
  куда ставится ble.sh; `tmux-sysstat` — в `.local/bin`, рядом с остальными
  своими скриптами;
- **шаблон `status-format[1]`** — это вклеенный дефолт tmux, нужный потому, что
  при `status 2` вторая строка иначе показывает индексы панелей. Он был снят с
  tmux 3.x и использовал `window_end_flag`, который 3.6 заменила на
  `loop_last_flag`. Перегенерирован из `tmux -f /dev/null show -g status-format`
  на установленной версии. **При обновлении tmux сверять заново.**

CPU и память в статусе считает `.local/bin/tmux-sysstat` — читает `/proc`, без
внешних зависимостей, сам рисует powerline-шапку и красит модуль целиком по
порогу. Подключается как `#()`, то есть выполняется живьём на каждый тик
(`status-interval 3`).

catppuccin **вендорится в модуль**, в `.local/share/tmux/catppuccin` — вопреки
общему правилу «всё внешнее через `modules/<модуль>/update`». Правило это про бинарники,
у которых неверная арка не диагностируется до запуска; здесь же обычные конфиги
tmux, и такой беды у них быть не может. Из апстрима взят только рантайм (26
файлов вместо 61): без `docs/`, `tests/` и линтерских конфигов. Версия — в файле
`VERSION`, сейчас v2.3.0.

### Переход по окнам с уровня sway

`$mod+Alt+h/l` в sway переключает окна tmux — это третий, самый внутренний
уровень навигации (столы → окна и табы sway → вкладки внутри окна). Детекта
приложения нигде нет: sway зовёт `.local/bin/content-tab`, тот синтезирует через
`wtype` обычное `Ctrl+PageUp`/`Ctrl+PageDown`, а понимают эту комбинацию все —
и Chrome, и tmux, которого научили двумя строками `bind -n C-PPage/C-NPage`.
Дальше всё чисто байтовое, и локальной стороне не надо знать, что внутри:

```
wtype → sway → kitty     не находит своего маппинга на Ctrl+PageDown
                         и пишет в pty xterm-escape \e[6;5~
        │
        ├─ в pty голый bash → ничего, мусор в приглашение не печатается
        ├─ в pty tmux       → C-NPage → next-window
        └─ в pty ssh        → байты уезжают в удалённый pty, там их читает
                              удалённый tmux и матчит тот же бинд
```

Поэтому по ssh это работает без единой локальной настройки — нужен только тот же
конфиг на удалённой машине (dev-воркспейсы тянут dotfiles сами). В уже живущей
сессии — `tmux source-file ~/.config/tmux/tmux.conf`.

**Вложенный tmux** (локальный, внутри него ssh и ещё один tmux) **не
поддерживается**: `bind -n` сработает во внешнем, до ssh, и внутренний ничего не
увидит. Если понадобится — лечится разводкой во внешнем tmux по
`#{pane_current_command}`, отдавая клавишу внутрь через `send-keys`.

## Буфер обмена и передача файлов

```sh
clip copy <файл>...     скопировать файлы
clip copy               скопировать текст со stdin
clip paste [каталог]    вставить (по умолчанию в текущий)
clip list               что сейчас в буфере
clip doctor             какая среда определилась и почему
```

Скрипт `.local/bin/clip`. Одинаковые команды на всех машинах: он сам понимает,
где запущен, и делает нужное.

### Почему это вообще проблема

Буфер обмена переносит **ссылку, а не байты**. Nautilus по `Ctrl+C` ничего не
копирует — он объявляет себя владельцем selection и по запросу отдаёт
`text/uri-list` с путём, а вставляющее приложение само открывает этот путь и
читает файл. Через ssh это ломается структурно: `file:///home/user/x` валиден
только на той машине, которая вставляет.

### Транспорт: TTY, а не сокет

Файлы возит `kitten transfer`, а он общается с локальной kitty
escape-последовательностями. TTY — прозрачная труба:

```
процесс в контейнере → PTY контейнера → dockerd → docker client на VM
   → PTY ssh-сессии → sshd → ssh → локальная kitty
```

Работает сквозь любую вложенность, включая jump-хост и `docker exec`, без
единого сокета, порта и без правок ssh-конфига. Требует ровно одного: бинарник
`kitten` в той среде — его ставит `modules/core/update`, отдельно от самой kitty
(терминал на сервере не нужен, нужен только клиент).

Отвергнутые альтернативы:

- **`wl-copy` по ssh** — пишет в буфер удалённой машины, а не своей. Ровно это
  уже разобрано в разделе «tmux»;
- **демон + unix-сокет через `ssh -R`** (модель `ssh-agent`) — работает, но
  требует правки ssh-конфига на каждый хост, не переживает `docker exec` без
  bind-mount сокета, и отдаёт каждой среде право молча читать твой буфер. TTY
  этих свойств лишён: канал живёт ровно столько, сколько открыт терминал;
- **`allow_remote_control`** — запрещён решением из «Сознательно не переносим».
  TTY-киттены его и не требуют;
- **base64 через OSC 52** — лимиты у терминалов дикие и разные (VTE молча режет
  на 4096 байт), для файлов не годится. Для текста — годится и используется.

### Как определяется среда

1. `$WAYLAND_DISPLAY` есть, `$SSH_CONNECTION` пуст → **локально**, работаем
   `wl-copy`/`wl-paste` напрямую;
2. иначе есть `kitten` и открывается `/dev/tty` → **киттены**;
3. иначе → OSC 52, только текст.

Не по `$TERM` и не по `$KITTY_PID`: внутри tmux `$TERM` это `tmux-256color`, а
`$KITTY_PID` по ssh не пробрасывается вовсе. И не через `[[ -r /dev/tty ]]` —
файл в devtmpfs есть всегда, тест проходит даже когда терминала у процесса нет,
а открытие тут же валится с ENXIO. Проверяем попыткой открыть.

Переопределяется переменной `CLIP_ENV=local|kitty|plain` — для отладки.

### Картинки

`clip paste` понимает не только ссылки на файлы, но и поток `image/*`. Это не
экзотика, а основной путь для скриншотов: `shot` открывает снимок в satty, и
`Enter` кладёт его в буфер **картинкой без имени файла** (`Ctrl+S` сохраняет в
`~/Pictures/Screenshots`, но это другой сценарий). Вставить такое как файл
раньше было нечем.

```sh
Print                    # снять область, Enter в satty — в буфер
clip paste               # → clip-20260809-183019.png в текущем каталоге
```

Имя выдумывается (`clip-ГГГГММДД-ЧЧММСС`), расширение берётся из MIME:
`image/png` → `.png`, `image/jpeg` → `.jpg` и так далее. Две вставки в одну
секунду разъезжаются суффиксом, как и обычные файлы.

Ссылки на файлы имеют приоритет над картинкой: если в буфере есть `uri-list`,
значит файл уже существует под своим именем и выдумывать новое незачем.

Работает в обе стороны — на удалённой машине то же самое делает
`kitten clipboard -g`, то есть снимок с рабочей станции забирается файлом прямо
в контейнер.

### Спул и чужой $HOME

Байты и ссылка едут разными каналами: файлы — через `kitten transfer`, в буфер
кладётся только опись (`#clip-spool-v1` первой строкой). Опись крошечная и
заведомо влезает в лимиты OSC 52, а файлы при этом любого размера.

Спул — `~/.cache/clip/current` на машине, за которой сидишь. Незнание чужого
`$HOME` снимается правилом `kitten transfer`: относительные пути на
**принимающей** стороне резолвятся от домашнего каталога. Поэтому удалённая
сторона пишет в `.cache/clip/current/`, не зная, где локальный HOME.

Каталог обязан существовать заранее — `kitten transfer` его не создаёт, а
удалённая сторона создать его на локальной машине не может. Заводит
`modules/core/update`, на каждой машине: «локальной» оказывается та, за которой
ты сейчас сидишь, и это может быть любая.

### История буфера обмена

Менеджеры истории (cliphist и родня) работают через `wl-paste --watch` и
сохраняют всё, что проходит через буфер. Опись спула — обычный текст, поэтому
она тоже туда попадёт. Отсюда неочевидная мина: достаёшь опись из истории через
час, жмёшь `clip paste`, а спул давно перезаписан другим копированием. Имена
совпадают, файлы на месте — и вставились бы **чужие файлы, молча**.

Поэтому опись несёт идентификатор партии, и тот же id уезжает в спул файлом
`.clip-id`. При вставке они обязаны совпасть:

```
❌ опись устарела: спул уже перезаписан другим копированием.
   Похоже, опись достали из истории буфера обмена. Скопируй заново.
```

На удалённой стороне `.clip-id` забирается той же пачкой, что и файлы, а всё
приезжает во временный каталог: пока id не сверен, класть что-либо в рабочий
каталог нельзя. Отдельной передачей его тащить не стали — это был бы второй
попап подтверждения на каждую вставку.

#### Как это устроено

`$mod+v` открывает `~/.local/bin/clip-history` — он же поднимает из sway два
вотчера (`clip-history daemon`), потому что `wl-paste --watch` следит ровно за
одним типом и без второго картинки в историю не попадали бы.

Пикер — **тот же самый wofi, что и лаунчер**, вплоть до файла стиля: wofi по
умолчанию читает `~/.config/wofi/style.css`, который собирает `theme-toggle
refresh`. Поэтому история наследует тему автоматически, а не повторяет её.
Отличия от `$mod+d` сведены в отдельный `~/.config/wofi/clip-history.conf`:
`show=dmenu` и включённые картинки. Отдельный конфиг, а не флаги в строке
запуска, — потому что соседний `config` жёстко задаёт `show=drun`.

Оттуда же две неочевидные настройки:

- `dmenu-print_line_num=true` — wofi возвращает **номер** выбранной строки, а не
  её текст. Иначе пришлось бы разбирать обратно `img:/путь:text:превью`, а
  превью это произвольное содержимое буфера, где двоеточий может быть сколько
  угодно. Префикс `dmenu-` обязателен: опции режима без него молча игнорируются.
  Нумерация с нуля (проверено на wofi 1.5.1).
- `image_size=48` — превью узнаваемое, но текстовые записи (их большинство) не
  раздуваются втрое. Полноразмерные PNG отдавать wofi нельзя: он декодирует их
  на каждом запуске, и полсотни скриншотов 1920x1080 дадут секунды задержки.
  Поэтому `clip-history` держит миниатюры в `~/.cache/clip-history/<id>.png`,
  уменьшая картинку прямо при декодировании (`size-prepared` у GdkPixbuf) и
  выкидывая из кэша то, что выпало из истории.

Вставка — `wtype`, тем же приёмом, что в `content-tab`. В терминалах это
`Ctrl+Shift+V`, а не `Ctrl+V` (в терминале он занят: literal-next в readline,
блочное выделение в vim), поэтому скрипт спрашивает у `swaymsg -t get_tree`
класс сфокусированного окна — **до** показа пикера — и сверяется со списком
терминалов в своей шапке.

#### Буфер после вставки не восстанавливается

Хотелось бы «вставить, не трогая буфер», но в Wayland это невозможно:
приложение забирает данные лениво, уже ПОСЛЕ `Ctrl+V`, и вернуть прежнее
содержимое раньше этого момента — значит вставить пустоту. Выбранное просто
остаётся в буфере, как после обычного копирования.

Побочный эффект так и задуман: свой же вотчер увидит `wl-copy` и запишет
выбранное заново, а cliphist схлопнет дубль (`-max-dedupe-search`). Запись не
размножается, а всплывает наверх — история сама становится MRU.

#### Тип содержимого

Формат хранения cliphist MIME не запоминает, так что при наивном `cliphist
decode | wl-copy` тип теряется. **Для картинок это починено**: `cliphist list`
показывает бинарь как `[[ binary data 10 KiB png 1920x1080 ]]` — тип видно прямо
в превью, оттуда он и уезжает в `wl-copy -t image/png`.

**Для `text/uri-list` — нет.** Файл, скопированный через `clip`, вернётся из
истории строкой `file://...` в `text/plain`, и файлом уже не вставится.
Восстанавливать по эвристике «все строки начинаются с `file://`» технически
можно, но это меняло бы поведение для текста, который просто выглядит как путь.
`clip list` показывает, какие типы реально лежат в буфере.

Скриншоты идут через буфер, так что история заполняется ими. Отсюда
`-max-items 200` вместо дефолтных 750 — флаг задан в `clip-history`, рядом с
пикером, который эту историю и читает.

### Границы

- **`cut` не поддерживается вовсе**, только copy. Удалять оригинал по факту
  вставки, которая могла не случиться, — способ потерять данные на ровном месте.
- **Вставка файла в GTK-приложение** работает через `text/uri-list`. GTK-специф-
  ичный `x-special/gnome-copied-files` туда не влезает: `wl-copy` умеет ровно
  один MIME-тип за вызов. Это плата за одну команду вместо демона.
- **`kitten transfer` показывает попап подтверждения** в kitty на каждую
  передачу, потому что `file_transfer_confirmation_bypass` не задан. Оставлено
  намеренно: это ровно модель `ssh-add -c`. Отключение потребовало бы положить
  пароль в среду удалённой машины, то есть отдать его любому коду, который там
  выполняется.
- **Среда без `kitten`** — работает только текст, выделением через tmux
  (`set-clipboard on`, см. «tmux»). Чтобы поднять её до файлов, `kitten` можно
  прибиндить с хоста при создании контейнера
  (`-v ~/.local/bin/kitten:/usr/local/bin/kitten:ro`) — устанавливать ничего не
  надо, это один статический бинарник.
- **Арка бинарника** должна совпадать с аркой контейнера: на arm64-хосте
  контейнер может оказаться amd64 под эмуляцией.

## Мониторы

`$mod+P` открывает nwg-displays: мониторы двигаются мышью, кнопка Apply меняет
раскладку в живой сессии. По закрытию окна раскладка снимается из sway и
записывается профилем в `~/.config/kanshi/config` — дальше kanshi применяет её
сам при каждом подключении этого набора мониторов.

```sh
display-setup             # то же, что $mod+P
display-setup save [имя]  # сохранить текущую раскладку, не открывая GUI
display-setup list        # что вообще есть в конфиге
```

Почему связка из трёх кусков, а не что-то одно:

- **sway** сам применяет `output`-блоки при hotplug и матчит монитор по
  «производитель модель серийник», а не по порту. Но описывает мониторы
  поодиночке и про их комбинации не знает: «воткнут внешний — погасить eDP-1»
  в его синтаксисе не выражается. Ради этого и взят kanshi.
- **kanshi** держит профиль на *набор* выходов целиком, но GUI у него нет.
- **nwg-displays** — GUI, но сохраняет только в sway-синтаксис
  (`~/.config/sway/outputs`), kanshi-формат он не умеет вовсе. Поэтому его файл
  отправлен в `$XDG_RUNTIME_DIR` и не используется, а профиль пишет
  `display-setup`, снимая уже применённую раскладку через `swaymsg`.

Тонкости, о которые легко споткнуться при ручной правке конфига:

- профиль матчится по **точному** набору выходов, поэтому двух профилей с
  одинаковым набором быть не должно: сработает первый, второй молча не
  применится никогда. `display-setup` поэтому заменяет профиль с тем же
  набором, а не дописывает второй;
- `kanshictl` в Debian/Ubuntu вырезан (тянет `varlink`, которого нет в архиве),
  так что перечитать конфиг на лету нечем — только перезапуск процесса, его
  делает и `display-setup`, и `exec_always` в конфиге sway;
- встроенная панель адресуется как `eDP-1` (имя порта у неё стабильно),
  внешние — как «производитель модель серийник», чтобы опознавались в любом
  порту. Точные строки: `swaymsg -t get_outputs`;
- если ни один профиль не подошёл, kanshi не делает **ничего** и выходы
  остаются как их разложил sway. Это безопасный исход, а не поломка.

⚠ Откат, если раскладка уехала и экрана нет: `Ctrl+Alt+F3` (TTY) или ssh, затем

```sh
pkill -x kanshi && swaymsg output '*' enable
```

Насовсем — убрать строку `exec_always ... kanshi` из конфига sway, больше она
нигде не прописана (systemd-юнита у пакета нет). Всё вернётся к штатному
поведению sway: новый монитор кладётся справа в дефолтном режиме.

## Тема (светлая/тёмная)

Клик по иконке ☾/☀ в панели или:

```sh
theme-toggle              # переключить
theme-toggle dark|light   # выставить явно
theme-toggle get          # какая сейчас
theme-toggle refresh      # заново применить текущую (зовётся сам)
```

Состояние ровно одно — gsettings `org.gnome.desktop.interface color-scheme`.
Из него портал кормит Chrome, Electron/VSCode и GTK, а `theme-toggle refresh`
раздаёт цвета тем, кто портала не знает: sway, kitty, waybar, wofi, btop.

Обе палитры (Catppuccin **Mocha** и **Latte**) лежат в одном месте —
`.local/bin/theme-colors`. Конфиги обращаются к цветам только по именам
ролей (`base`, `surface0`, `text`, `blue`…), поэтому светлая тема — перенос один
в один, а третью можно добавить, не трогая ничего, кроме генератора.

```sh
theme-colors kitty|sway|css|btop [dark|light]   # посмотреть, что получит потребитель
```

Без второго аргумента генератор выясняет тему сам, перебором от самого
осведомлённого источника к самому общему:

1. **gsettings** — сессия рабочей станции, единственное место, где тему реально
   выбирал человек. Смотрим код возврата, а не только текст: `gsettings` бывает
   установлен и без схем — на `tihonove-ivm` он отвечает `No schemas installed`,
   и раньше этот мусор проходил как «светлая тема»;
2. **терминал** — на удалённой машине и в контейнере спросить gsettings нельзя, а
   вот терминал, в котором всё это рисуется, свой фон знает. Спрашиваем его
   escape-последовательностью OSC 11 (`\e]11;?`) на `/dev/tty`, ответ `rgb:…`
   переводим в яркость по Rec. 709 и сравниваем с серединой. Запас огромный —
   Mocha даёт 31 из 255, Latte 240, так что гамму разворачивать незачем. Через
   ssh это работает само (обычный поток терминала), сквозь tmux тоже: проверено
   на 3.6 — он отдаёт фон внешнего терминала, а не свою догадку;
3. **dark** — если не ответил никто (нет управляющего терминала: cron,
   systemd, `ssh host cmd` без tty).

Читателя тут заботит только один потребитель — btop, единственный, кому палитру
надо испечь файлом заранее. Остальные либо живут на машине со sway (waybar,
wofi, sway), либо спрашивают генератор сами при каждом старте (kitty).

Доставка у каждого своя — по тому, что он умеет:

- **kitty** — `geninclude theme.sh` в `kitty.conf`: kitty **сам запускает**
  генератор при каждой загрузке конфига, так что файла с текущей темой на диске
  не нужно вовсе. Будится сигналом `SIGUSR1`, цвета применяются к уже открытым
  окнам. `allow_remote_control` для этого не нужен.
- **sway** — цвета уходят рантайм-командами через `swaymsg`. Не `reload`: тот
  перевыполняет `exec_always`, а там `pkill waybar` и `pkill kanshi`. Тёмные
  `client.*` в конфиге остаются дефолтом стартового кадра, на светлой их
  перекрывает `exec_always ... theme-toggle refresh` (он же чинит тему после
  `$mod+Shift+C`).
- **waybar** — палитра лежит рядом со `style.css` отдельным `colors.css` (в git
  его нет, это производное состояние) и подключается `@import`'ом; после записи
  `refresh` шлёт панели `SIGUSR2`. Её собственный `reload_style_on_change`
  включать не надо: моргает она одинаково в обоих случаях, но после вотчера
  разъезжаются зоны клика.
- **wofi** — `@import` не понимает вовсе: он грузит css через `load_from_data`,
  без базового пути, и на нерезолвнутом импорте теряет весь стиль (рисуется
  дефолтной GTK-темой). Поэтому в git лежит шаблон `style.css.in`, а рабочий
  `style.css` склеивает `refresh` — палитра плюс шаблон. Править надо шаблон.
- **btop** — тема кладётся файлом `.config/btop/themes/catppuccin.theme` (в git
  его нет, производное), а `btop.conf` ссылается на него по фиксированному
  имени: при переключении меняется содержимое файла, а не имя, и сам конфиг
  трогать не приходится. Разбудить btop нечем — тему он читает только при
  старте, ни сигнала, ни слежения за файлом у него нет, так что запущенный
  доживает в старой палитре до перезапуска. Файл пишет не только `refresh`, но
  и `modules/core/update`: на машине без sway звать `refresh` некому, а без
  файла btop молча свалился бы в тему `Default`.

  На удалённой машине этого мало, и раньше btop там поднимался **белым**: файл
  пекся один раз при установке, а `theme-colors` без внятного ответа от
  gsettings считал тему светлой. Поэтому, во-первых, `theme-colors` теперь
  спрашивает сам терминал (см. ниже), а во-вторых, рядом с конфигом лежит
  обёртка `.local/bin/btop`: она переписывает файл темы перед каждым запуском и
  передаёт управление настоящему бинарю. Спрашивать надо именно в момент
  запуска — между установкой и запуском тема сессии меняется сколько угодно раз.
  Обёртка шадовит бинарь по имени осознанно: отдельное имя или алиас пришлось бы
  помнить, и оно не сработало бы из чужих скриптов и биндингов.

  Почему нельзя проще, палитрой из цветов терминала (kitty их и так красит
  правильно в обеих темах): формат `.theme` держит только hex, пустая строка
  допустима лишь у `main_bg` и у mid-точек градиентов. Палитру обязательно надо
  испечь заранее — значит, кто-то обязан решить, какую.

Переменной окружения тут не обойтись: env уже запущенного процесса неизменяем, а
`swaymsg reload` читает тот же замороженный env. Подробный разбор —
`~/.system-setup/theme-light-dark.md`.

## devsy

```sh
~/.dotfiles/modules/devsy/update   # ставит CLI
~/.dotfiles/modules/devsy/setup   # настраивает ssh-провайдер (идемпотентно)
```

Перед первым запуском `modules/devsy/setup` нужен `~/.config/devsy-setup.conf` — адрес
машины и путь агента, в репе их нет (см. «Инвентарь»). Без файла скрипт
останавливается и печатает шаблон.

Заход в контейнеры — через `~/.ssh/config`, пользователем `vscode`, а не root.
Сами `Host`-блоки лежат в `~/.ssh/config.d/local.conf`, в репе — только шаблон
и объяснение, почему именно так:

```sh
ssh <имя>.devsy       # то же самое: devsy ws ssh <имя> --user vscode
ssh devsy-host        # сама облачная машина
```

Воркспейсы живут контейнерами на облачной машине, а их метаданные — локально в
`~/.devsy/contexts/default/workspaces/`. На новой машине этих метаданных нет, и
`devsy ws up` поднимет **новый** контейнер вместо подключения к старому. Как
восстановить метаданные из копии, которую держит агент на хосте, — расписано в
конце `modules/devsy/setup`.

## Сознательно не переносим

Решённое, чтобы не возвращаться при следующем заходе в `~/dotfiles-old`:

- **kitty remote control** — `allow_remote_control` + `listen_on unix:/tmp/kitty`
  и `ssh.conf` с `forward_remote_control yes`. Первое было нужно yazi, второе —
  открытию локального VSCode из ssh-сессии и отдаёт удалённому хосту управление
  локальным kitty. Не берём ни в каком виде.
- **вендоренное в git** — `.starship.arm` / `.starship.x86` и каталог
  `.ble-nightly/` на 4 МБ. У бинарников неверная арка не диагностируется до
  запуска: на aarch64 32-битный не падает, а вешает старт шелла. У `.ble-nightly`
  беда мягче, но та же по природе: `update-vendored.sh` его не обновлял, и он
  просто протухал в репе. Всё внешнее — через `modules/<модуль>/update`.
  Одно исключение — catppuccin для tmux, см. «tmux»: это конфиги tmux, не
  бинарник, так что беды с архитектурой у него быть не может.
- **kitty.cage.conf** — обвязка для cage (киоск), самого cage в системе нет.
- **foot** и **swayidle** — приехали как Recommends/Suggests к пакету `sway`
  (ставился без `--no-install-recommends`) и лежали без дела: терминал у нас
  kitty, а swayidle без swaylock и без строки в конфиге не запускался вообще.
  Удалены, вместе с осиротевшими `libfcft4t64` и `libutf8proc3`. Вернутся, если
  когда-нибудь переставлять `sway` без `--no-install-recommends`.
  **wmenu** оттуда же, но оставлен: это дефолтный лаунчер стокового
  `/etc/sway/config`, минималистичный dmenu под wlroots — держим как запасной
  вариант, пока приживается wofi.

Отложено, не забыть:

- **Super → tmux, отправляющая сторона** — сам tmux перенесён вместе с
  `user-keys` (см. «tmux»), но 22 маппинга `map super+... send_text` в
  `kitty.conf` не восстановлены, поэтому бинды пока лежат мёртвым грузом.
  Отдельная сложность: Super+1..9 забирает sway под столы и перехватывает их на
  уровне композитора, до kitty, — так что `User2..User10` не оживут, пока схема
  не разведена. Либо переводить окна tmux на другой модификатор, либо
  освобождать Super у sway.
  **Частично снято:** переход по окнам (`User18`/`User19`) больше не нужен —
  он решён через `$mod+Alt+h/l` и `Ctrl+PageUp/PageDown`, см. «tmux». Этот путь
  ту сложность обходит целиком: клавиша не Super, перехватывать её sway незачем,
  и посредник в виде kitty не нужен вовсе. Остаются окна 1..9, панели и лейауты —
  их той же схемой не покрыть, комбинаций на всех не хватит.
- **tmux-battery** — батарейный сегмент статуса убран при переносе: модуль
  catppuccin разворачивается в форматы плагина `tmux-battery`, а плагина нет.
  Вернуть можно только вместе с ним.

## Пакеты

Ставятся руками, в репу не входят:

```sh
# глифы TUI Claude Code: ⏵ (U+23F5) в строке режима, ⎿ (U+23BF) в дереве тулов.
# Ни Nerd Font, ни Noto Color Emoji их не содержат — рисуются пустыми квадратами.
# Не скачивается модулем, в отличие от двух других шрифтов: у Symbola нет ни
# релизов, ни версионированного источника — только зеркала с файлом в master.
# Пакет дистрибутива надёжнее. modules/kitty/update её наличие ПРОВЕРЯЕТ и
# печатает эту команду, если не нашёл, — молча пустых квадратов больше не будет.
sudo apt install --no-install-recommends fonts-symbola

# мониторы, см. раздел «Мониторы». wlr-randr — не для скриптов, а чтобы
# посмотреть выходы глазами, когда sway-сессии под рукой нет.
sudo apt install --no-install-recommends kanshi nwg-displays wlr-randr

# синтез нажатий через virtual-keyboard: им живут .local/bin/content-tab
# (третий уровень навигации, $mod+Alt+h/l, см. раздел «tmux») и clip-history
# (вставка выбранного из истории, см. «История буфера обмена»).
sudo apt install --no-install-recommends wtype

# хранилище истории буфера обмена под $mod+v, см. «История буфера обмена».
# Модуль sway держит его в requires — без пакета install.sh откажется ставить
# сессию целиком.
sudo apt install --no-install-recommends cliphist

# jq: им живёт индикатор раскладки .local/bin/lang-status — фильтрует поток
# событий `swaymsg -t subscribe` (--unbuffered, строка на событие). Тоже в
# requires у sway, как и cliphist.
sudo apt install --no-install-recommends jq

# fzf ставит modules/core/update — бинарником в ~/.local/bin, без sudo и
# свежее пакетного. Пакет тоже годится и, если он уже стоит, установщик его
# не трогает; ставить специально незачем (см. «fzf»).

sudo apt install --no-install-recommends brightnessctl
sudo install -m 644 system/90-backlight.rules /etc/udev/rules.d/
sudo udevadm control --reload && sudo udevadm trigger -s backlight -c add
sudo usermod -aG video "$USER"   # применяется после релогина
```

### tailscale

Не через `modules/<модуль>/update`: это системный демон с юнитом systemd и правами на
`/dev/net/tun`, а не бинарник в `~/.local/bin`.

```sh
curl -fsSL https://pkgs.tailscale.com/stable/ubuntu/resolute.noarmor.gpg \
    | sudo tee /usr/share/keyrings/tailscale-archive-keyring.gpg >/dev/null
sudo chmod 644 /usr/share/keyrings/tailscale-archive-keyring.gpg
sudo install -m 644 system/tailscale.sources /etc/apt/sources.list.d/
sudo apt update && sudo apt install --no-install-recommends tailscale

sudo tailscale up   # интерактивно: печатает ссылку, авторизация в браузере
```

Апстрим отдаёт только `.list` в старом формате — в `system/tailscale.sources`
лежит тот же репозиторий в deb822, как остальные источники в системе. Suite
прибит к `resolute`, архитектура к `arm64`: машина одна, при апгрейде релиза
Ubuntu файл надо править руками.
